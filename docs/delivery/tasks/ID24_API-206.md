## 1. Контекст и цели задачи

В рамках управления рисками Семинара 6 за Филиппом Маркусом закреплены критические риски подсистемы интеграций и данных:
- **R05** (Интеграции): Недоступность источника ответов LLM (сетевой timeout, 429 Rate Limit, 5xx Server Error) ($P=4, I=4, S=16$ — критический).
- **R06** (Данные): Некорректный или искажённый usage от внешнего провайдера (отрицательные токены, пропуски полей, boolean вместо чисел) ($P=3, I=4, S=12$ — высокий).
- **R07** (Данные): Дрейф контрактов и недопустимые изменения схемы внешнего API ($P=3, I=4, S=12$ — высокий).

Цель работы — исключить финансовые потери и зависание клиентских сессий при сбоях провайдеров, подтвердить изоляцию сбоев автотестами без использования платных боевых ключей.

## 2. Реализованный результат

1. **Mock-провайдер с эмуляцией сценариев сбоев (`internal/mockprovider/`)**:
   - Реализована обработка заголовка `X-Mock-Scenario` для симуляции граничных состояний:
     - `rate_limit`: возврат HTTP 429 с телом `{"error":{"code":"rate_limit_exceeded","message":"Rate limit reached"}}`.
     - `server_error`: возврат HTTP 500 с кодом ошибки `server_error`.
     - `timeout`: принудительное удержание соединения с прерыванием по контексту клиента.
     - `bad_usage`: возврат ответа с некорректным значением токенов (`completion_tokens: -1`) для проверки отклонения валидатором.
     - `invalid_json` / `missing_input`: возврат HTTP 400 и HTTP 422 при симуляции schema mismatch.

2. **Контрактные тесты валидации схемы и качества данных (`tests/contracts.test.mjs`)**:
   - В тестовый набор включены строгие проверки контракта канонической схемы:
     - `canonical rejects negative tokens`: отказ при отрицательных токенах.
     - `canonical rejects boolean tokens`: отказ при некорректных типах данных в блоке usage.
     - `canonical rejects missing user content` и `canonical rejects unknown parameter`: отсечение дрейфа схем внешних провайдеров.
     - `canonical response preserves all token categories`: полная проверка категорий токенов (`prompt_tokens`, `completion_tokens`, `cached_tokens`, `reasoning_tokens`).

3. **Связка с биллинговым контуром**:
   - Проверено требование: при возврате HTTP 429, 500 или timeout вызов шлюза считается неуспешным, финансовый hold баланса клиента полностью освобождается, списание средств не производится.

## 3. Критерии приёмки (DoD) и верификация

| Критерий DoD | Факт проверки | Статус |
|---|---|---|
| Timeout ограничен клиентской настройкой | Проверен тестом `TestCanceledTimeout` через контекст Go | Выполнено |
| Неуспешный вызов (429, 500, timeout) не списывает средства | Проверена логика освобождения hold при ошибках провайдера | Выполнено |
| Отрицательные токены и bool вместо числа отклоняются | Проверено в `tests/contracts.test.mjs` (тесты `canonical rejects negative tokens`, `boolean tokens`) | Выполнено |
| Локальный прогон автономен и не требует боевых ключей | Запуск тестов mock-провайдера и схемы полностью локален | Выполнено |
